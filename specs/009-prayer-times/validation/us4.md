# Qiyam implementation checkpoint — 2026-10-30

Status: implementation complete for the native short-notification path; **T072 device acceptance remains OPEN**. Full athan/audio acceptance is not implied.

Qiyam is derived from the selected convention's Maghrib and following Fajr by elapsed UTC duration: `Maghrib + 2 × (following Fajr − Maghrib) / 3`, rounded once to the nearest displayed minute. Invalid/non-positive boundaries produce no Qiyam. Upcoming time uses the active location's zone and actual local delivery date. Both the UI and scheduler consider the previous evening after midnight; a regression first demonstrated a one-day scheduling error and now protects that boundary.

Qiyam defaults off, uses an original non-verbal tone, and can be enabled with all daily prayer switches off and no athan recording available. An unavailable daily recording does not block Qiyam; a blocked Qiyam channel does not block supported daily prayers. Disabling Qiyam preserves daily choices and reinstalls only their valid future events under the new generation. Active-place and convention changes recompute Qiyam; merely viewing another place does not change it.

The scheduler shares the total finite horizon: next 60 events on iOS, up to 30 elapsed days on Android. It queues one Qiyam per valid night, with opaque IDs, no past events and no boot-time audio start. Android rejects delivery beyond its 60-second expiry. iOS owns local presentation and cannot run an app expiry check before delayed presentation (P07); that limitation is disclosed. Inexact Android alarms are explicit opt-in and may be skipped if late.
