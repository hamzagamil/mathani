# Research: Jumu'ah Alerts, Duha Reminder and Announcements

## R1. Which day is Friday

- **Decision**: `DaySchedule.localDate.weekday == DateTime.friday`. `localDate` is the place's
  date as a UTC midnight, so its weekday is the place's weekday regardless of the phone's zone.
- **Rationale**: matches the spec's "Friday by the place's clock" edge case with no extra code.
- **Alternatives**: the phone's local weekday (wrong for a fixed city in another zone).

## R2. The Friday Dhuhr alert keeps its kind

- **Decision**: the alert stays `PrayerKind.dhuhr` with the same id and sound; only its title
  uses the Jumu'ah name. The schedule row keeps `dhuhr` and changes its label.
- **Rationale**: ids are stable (`alertId(place, date, kind)`), Android channels and the athan
  service treat it as a prayer, and FR-001 says only the title changes.
- **Alternatives**: a `jumuah` prayer kind replacing Dhuhr on Fridays (would change ids, sounds
  and every `dailyPrayers` check).

## R3. Two new reminder kinds

- **Decision**: `PrayerKind.jumuah` (the 20-minute reminder) and `PrayerKind.duha`, handled like
  `qiyam`: Qiyam's sound (`toneSound`, the takbira), Qiyam's Android channel, no full athan, not
  in `dailyPrayers`. The Android store accepts the two names. The Qiyam channel's display name
  becomes "Reminders" ("التذكيرات"); its id is unchanged, so the reader's channel settings stay.
- **Rationale**: the spec asks for the same sound as Qiyam; one channel for reminders keeps the
  phone's settings simple.
- **Alternatives**: a new Android channel per reminder (more settings, no benefit).

## R4. Jumu'ah reminder default (spec Q1)

- **Decision**: `AlertSettings.jumuah` is `bool?`. `null` = the reader never changed it, and the
  effective value is `prayers.contains(dhuhr)`. Turning the row on or off stores `true`/`false`.
  Old saved JSON has no key, so updates follow Dhuhr automatically (FR-005, FR-022).
- **Alternatives**: a migration that writes the Dhuhr value once (then later Dhuhr changes would
  not carry over, contrary to scenario 7).

## R5. Duha time (spec Q2)

- **Decision**: `duhaUtc = sunrise + (dhuhr − sunrise) / 2`, from the adjusted events, rounded to
  the nearest minute; `null` if either is unavailable.
- **Sources**: Sahih Muslim 748 ("صلاة الأوابين حين ترمض الفصال"); the start (sun a spear's height,
  ~12–20 min after sunrise) and end (a few minutes before zawal) are in the spec. The midpoint is
  always inside that window, so no clamping is needed.

## R6. Push service

- **Decision**: Firebase Cloud Messaging with `firebase_core` and `firebase_messaging`, no
  `firebase_analytics`. Auto-init off (Android manifest meta-data, iOS Info.plist), so no token is
  created until the Announcements switch is on and the app starts messaging after the first
  frame. Firebase options come from `lib/firebase_options.dart` generated by `flutterfire
  configure` (no Gradle plugin, no plist file). Until that file holds a real project, start-up
  fails quietly and announcements stay inactive.
- **Rationale**: the owner asked for the FCM console. Without Analytics nothing but the
  installation id and token leaves the phone (FR-017).
- **Alternatives**: see plan Complexity Tracking.

## R7. Audiences: topics

- **Decision**: subscribe to `all` and to `lang_ar` or `lang_en` (the app's language), and
  re-subscribe when the language changes. Off → unsubscribe from all three.
- **Rationale**: the console's language and country targeting needs Google Analytics; topics do
  not. Topics also keep "everyone" separate from future segments (spec assumption) and make
  "off" reliable: nothing is ever sent to a single token.
- **Alternatives**: deleting the token when off (also works, but topics are needed anyway).

## R8. Showing and tapping

- **Decision**:
  - Background/closed: the system shows the message. Android uses the channel
    `announcements_v1` (manifest default channel, default importance, "Announcements from
    Mathani"). iOS uses the APNs alert.
  - Foreground: Android posts it through `flutter_local_notifications` on the same channel; iOS
    sets foreground presentation to banner and list without sound.
  - Tap: `getInitialMessage()` and `onMessageOpenedApp` read `data.link`. If it is an `https`
    link on `mthani.app`, `www.mthani.app` or `get.mthani.app`, it goes into the link stream that
    `GroupLinkHost` already reads. Other links are ignored and the app just opens.
- **Rationale**: no background isolate or handler is needed (Principle III, IV).

## R9. Permission

- **Decision**: never asked at start. Turning the Announcements switch on asks for notification
  permission if it was never asked. Turning on a prayer alert keeps asking as today. Topics are
  subscribed regardless; delivery shows once permission exists.

## R10. Priority when the alert list is full

- **Decision**: `nearestAlerts` sorts by time and takes `max`. Then, only within the last day of
  that window, kept reminders give way to prayer alerts of the next day that were cut, and the
  list is re-sorted. Swapping across the whole window was rejected: it would drop today's Qiyam
  for a prayer a week away, against "nearer alerts are never dropped". The window refills on
  every start and resume, so the far edge is always about a week ahead.

## R11. Owner actions (outside code)

- Create the Firebase project, run `flutterfire configure` for Android and iOS, upload the APNs
  auth key, add the Push Notifications capability to the App ID, regenerate the App Store
  provisioning profile (secret `IOS_APPSTORE_PROFILE_BASE64`), then add `aps-environment`
  (`development`) to `ios/Runner/Runner.entitlements`. Until then the entitlement stays out, or
  signing with the current profile fails, and iOS receives no announcements.
- Update App Privacy (Device ID, App Functionality, not linked, not tracking) and Data safety
  (Device or other IDs, collected, app functionality, not shared) as listed in
  `docs/store/privacy.md`.
